# AI 口播功能前端交互与布局设计方案

> 日期：2026-11-01
> 方法：GitHub 同类项目前端实测调研（来源逐条附后）+ 本项目代码底座核对，不含无依据推断。

---

## 一、调研结论：同类项目怎么做前端

### 1.1 对标项目 OPEN VIDEO EDIT（kevinbadi/open-edits）——没有网页前端

关键事实：它是 **Claude Code 技能包**（`skills/*/SKILL.md` + `scripts/*.py`），README 原文 "No timeline, no templates you drag around"。它的交互模式是：

| 环节 | 做法 |
|---|---|
| 启动 | 纯对话：终端输入 `edit this talking head: ~/Downloads/my-clip.mov`，无表单无上传控件 |
| 布局 | 即终端聊天流，无时间轴/预览窗/参数面板 |
| 进度 | Agent 工具调用输出即进度（prep_talking_head.py 转写 → 抓素材 → 生成 render.py → 预览帧碰撞检查 → ffmpeg 渲染） |
| 迭代 | 成片后自然语言二改（"make the intro darker"），重写 render.py 重渲染 |

→ 对我们的启示：**对话驱动是这类"原片增强"剪辑的天然形态**（管线与我们的 talking_head_overlay 完全同构），但纯对话缺 Web 进度反馈和可视化预览。

### 1.2 有 Web 前端的项目：四种范式

| 项目 | 启动 | 布局 | 进度 | 迭代 |
|---|---|---|---|---|
| [MoneyPrinterTurbo](https://github.com/harry0703/MoneyPrinterTurbo) | 表单（主题→AI 生成文案→可编辑） | Streamlit 三栏：脚本/素材音频/字幕样式 | 后台任务 + 页面状态 | 改表单重跑 |
| [NarratoAI](https://github.com/linyqh/NarratoAI) | 上传视频→生成解说脚本 | 参数面板+视频区分块 | **模态框：总进度条 + 6 步骤清单，当前步高亮**（`webui.py` L114-318，0.5s 轮询） | 改文案重生成 |
| [ShortGPT](https://github.com/RayVentura/ShortGPT) | **聊天状态机**（横竖屏→TTS→语言→脚本→YES/NO 确认） | 3 Tab，任务区=聊天窗+输入框 | gr.Progress + 逐步日志 | 对话修正后重做 |
| [FunClip](https://github.com/modelscope/FunClip) | 上传→识别→点选文本→剪辑 | Gradio 左右两栏 | 仅按钮加载态 | 重选段再点 |
| [OpenCreator (KrillinAI)](https://github.com/krillinai/OpenCreator) | **双通道：表单或自然语言对话** | "对话+可视化工作区共享同一状态机"；字幕沉浸式编辑器 | 分项 completed/total 计数 | **版本化：每次修改生成新版本，可回退对比** |
| [OpenChatCut](https://github.com/0xsline/OpenChatCut) | agent 对话 | agent 工作区+媒体池+预览+多轨时间轴 | 同屏执行轨迹 | 编辑写入真实轨道，可 undo/存版本 |
| [OpenReel](https://github.com/Augani/openreel-video) | "Describe → review plan → model edits" | 四栏：素材左/预览中/AI 聊天右/时间轴下 | event-sourced 命令日志 | **AI 每轮在隔离草稿执行，成功才提交快照，支持 Undo last AI turn** |

### 1.3 提炼出的行业共性（每条有上文出处）

1. **中间产物先行**：脚本/剪辑计划总先生成、以可读形式呈现，用户确认后才进渲染管线（ShortGPT 的 YES/NO、OpenReel 的 review plan、FunClip 的点选文本）。
2. **进度 = 阶段清单 + 细粒度百分比**：NarratoAI 的六步高亮 + ffmpeg 百分比是公认最佳实践。
3. **出片就地内嵌 `<video>` 预览 + 下载/发布**，无一例外。
4. **迭代方式演进**：改表单重跑 → 对话修正 → 版本快照可回退（OpenCreator/OpenReel 已成高级项目共识）。
5. **双模共享状态**（OpenCreator）：聊天发指令、面板做精调，二者同步——最契合"聊天式多智能体平台"的方向。

## 二、我们的底座：已有什么、缺什么

### 已有（直接复用，不新建）

| 能力 | 位置 |
|---|---|
| 视频上传（≤5 个、≤500MB → asset_id） | [useChatVideos.ts](../frontend/src/components/chat/composables/useChatVideos.ts)，走 `/api/video-assets` |
| 聊天触发口播技能 | [chat_agent.py L889-911](../backend/app/api/routers/chat_agent.py)：上传后注入 video_asset_ids，LLM `skill_call('talking_head_overlay')` |
| 闸门确认卡模式 | StoryboardConfirmCard（分镜确认）、ClarificationCard、GuardianConfirmCard——成熟的"先确认后执行"交互范式 |
| 视频进度缩略组件 | [VideoRenderer.vue](../frontend/src/components/chat/renderers/VideoRenderer.vue)：progress prop（skill/step/percent/detail）+ hover 播放 |
| SSE 契约单一事实源 | [sse-contract.ts](../frontend/src/components/chat/sse-contract.ts) |
| 视频大图预览 | VideoLightbox.vue |

### 缺口（本次要补的）

1. **`video_pipeline_progress` 事件前端未接**——sse-contract.ts L37 明确记录"skills 发 video_pipeline_progress / multi_image_video_progress，前端未接"。口播进度对用户完全不可见。
2. **无"剪辑方案确认"闸门卡**——LLM 规划出的叠加计划（几十个叠加、模板分布、时间轴）用户在渲染前看不到，渲染后才发现不满意，浪费几分钟渲染时间。这违背行业共性 1。
3. **无版本化迭代**——改一句话重跑就覆盖旧片，无法对比回退。

## 三、设计方案：聊天流为主轴的"轻双模"

### 3.1 总原则（来自调研，不自创）

- **不做独立全屏时间轴编辑器**。OpenChatCut/OpenReel 的四栏编辑器是多轨精细剪辑的形态，投入大；我们的口播是"原片 + 叠加增强"单主轨模式，行业对标（open-edits）也证明对话驱动足够。精细调整走对话 + 轻量确认卡。
- **采用 OpenCreator 的"双模共享状态"**：聊天是唯一入口，出片后的调优指令（"字幕再大一点""去掉第 3 段的箭头"）通过 SSE 增量更新同一张任务卡，而不是新开页面。

### 3.2 交互流程（四阶段状态机）

```
用户上传视频附件
      │
      ▼
[阶段1 澄清]  ClarificationCard（已有组件）
      │  风格档位（克制/活泼/教学）/ 叠加密度 / 是否生成封面
      ▼
[阶段2 方案确认]  ★新增 CutPlanConfirmCard（对标 ShortGPT YES/NO + OpenReel review plan）
      │  展示：叠加计划摘要（N 个叠加 × 模板分布）
      │       叙事分段（开场/论点/收束，来自 P2 两步链的中间层）
      │       时间轴条带（可横向滚动的迷你时间轴，叠加以色块标注）
      │  按钮：[开始渲染] [调整方案（发消息继续对话）]
      ▼
[阶段3 渲染进度]  ★接通 video_pipeline_progress → ProgressCard
      │  复用 NarratoAI 模式：阶段清单（转写→规划→抽帧→合成→审片）
      │  + 总百分比。渲染在聊天流中原位更新，不弹模态框
      ▼
[阶段4 出片]  VideoRenderer 内嵌预览 + VideoLightbox 大窗
      │  ★新增：版本条（v1 v2 v3 可切换回退，对标 OpenCreator）
      │  快捷指令 chips：「字幕更大」「节奏加快」「去掉某段」「换个风格重出」
      └── 点 chips 或直接打字 → 走 [阶段2] 重新确认（增量方案）→ 重渲染
```

### 3.3 布局设计（贴现有 ChatView 结构）

不改变 ChatView 现有骨架（消息主列 + ContextSidebar 右侧栏），口播的全部交互以**消息内卡片**承载：

```
┌─────────────────────────────────────────────┬──────────────┐
│  ChatView 消息主列                            │ ContextSidebar│
│                                             │ （已有，不动） │
│  [用户] 我上传一段口播，帮我做成成品            │              │
│                                             │              │
│  [assistant 消息内卡片流]                     │  上下文资产    │
│  ┌───────────────────────────────┐          │  · 原片缩略   │
│  │ 🎬 口播增强                     │          │  · 素材/脚本  │
│  │ ── 阶段指示器：●方案 ─○渲染 ○成片──│          │  · 版本历史   │
│  │                               │          │              │
│  │ ▸ 方案确认卡（CutPlanConfirmCard）│          │              │
│  │   叙事分段 3 段 · 叠加 18 个      │          │              │
│  │   [迷你时间轴条带 ▂▃▅▂▇▃▁▅▂]     │          │              │
│  │   模板分布：字幕×7 卡片×11       │          │              │
│  │   [开始渲染] [要调整→继续说]      │          │              │
│  └───────────────────────────────┘          │              │
│  （渲染中同一张卡原位变为进度态：阶段清单+%）    │              │
│  （完成后原位变为成片态：<video> 预览+版本条）   │              │
└─────────────────────────────────────────────┴──────────────┘
```

要点：
- **一张卡贯穿四阶段**（方案 → 进度 → 成片 → 版本），同一 DOM 原位状态切换，避免聊天流里刷出多张重复卡片。依据：OpenChatCut/OpenReel 的"同屏执行轨迹"共性，也符合本项目 ToolCallCell 执行轨迹的既有风格。
- **ContextSidebar 承担版本历史**：每次重渲染在 sidebar 追加版本项（v1/v2…），点击可回看任一版本成片。这是 OpenCreator 版本化共识在聊天式布局里的落位。
- **启动入口零学习成本**：不新增页面、不新增路由。用户在聊天里上传视频（已有能力）即触发，或在输入框 chips 中加一个「AI 口播」快捷入口（对齐 HomeView 快捷指令既有模式）。

### 3.4 新增/改动清单（前端）

| # | 改动 | 类型 | 对应缺口 |
|---|---|---|---|
| 1 | sse-contract.ts 增补 `video_pipeline_progress` 进 Ev 表 + useChatSSE 消费 | 改 | 缺口 1 |
| 2 | 新增 `CutPlanConfirmCard.vue`（方案确认卡，含迷你时间轴条带） | 新 | 缺口 2 |
| 3 | 新增 `VideoTaskCard.vue` 容器（四阶段状态机：plan/progress/done/version） | 新 | — |
| 4 | 后端渲染完成后发版本号，前端版本条 + ContextSidebar 版本历史 | 改（需后端配合加 `version` 字段） | 缺口 3 |
| 5 | 输入框快捷 chips 加「AI 口播增强」入口 | 改 | — |

后端仅需小改：`video_pipeline_progress` 载荷补 `phase` 枚举（transcribe/plan/render/review）与 `version`；方案确认闸门复用 storyboard_confirmation_required 的闸门机制（session L344 已有成熟模式）新增 `cut_plan_confirmation_required` 事件。

### 3.5 明确不做（防止过度设计）

- ❌ 独立时间轴编辑页/多轨编辑器（调研依据：单主轨口播不需要；open-edits 无 Web 前端照样达成效果标准）
- ❌ 模态框进度弹窗（NarratoAI 用模态是因为 Streamlit 页面无法原位更新；我们是流式聊天界面，原位卡片体验更好）
- ❌ 参数表单面板（叠加参数全部走自然语言 + 预设档位，符合"参数化/配置化演进"的既定方向）
