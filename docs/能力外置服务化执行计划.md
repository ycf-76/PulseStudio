# 能力外置服务化执行计划（内核-能力分层方案 · 五期）

> 版本：v1.0（2026-10-20）
> 状态：方案评审稿，待大哥批准后按期执行
> 前置：四期（ended_reason / 协议带 / 能力服务化机制 / 技能热加载）已全部落地，tag `phase4-hot-reload` → `kernel-pure`
> 一句话：把"没必要内置"的重能力按域拆成外部服务，主 API 进程彻底瘦身；用已有的 capability.toml + CompositeTransport 把拆解变成声明式配置。

---

## 1. 现状盘点（代码证据）

### 1.1 双体系已就位，中间断着

| 体系 | 已有 | 缺口 |
|---|---|---|
| **capabilities 能力包**（`capabilities/capability.toml`） | 9 域分包（scrapling / content_search / image_gen / video / messaging / copywrite / pool_monitor / rpa / account）、`enabled` 声明式开关、11 个 content sources 插件化、app/skills 下全是 shim 壳 | 只管「**有什么能力**」的开关，不管「**在哪跑**」 |
| **三期服务化机制**（`engine/protocol/transport.py` + `capability_service/`） | HttpTransport + CompositeTransport（按工具名路由）、grid_detect / grid_split 已真实外置（:8100）、双跑契约测试 | 只有一个服务实例，无分域服务拓扑、无长任务进度通道 |

**评估结论：拆解的内容维度已收口，缺的是执行位置维度。** 本计划不新造机制，把两者接起来。

### 1.2 重依赖分布（进程内痛点清单）

| 位置 | 依赖 | 痛点 |
|---|---|---|
| `app/cards/export.py` | playwright + **chromium**（async） | 浏览器进程驻留主 API：内存大、启动慢、崩溃连带 |
| `app/services/qr_worker.py` | playwright（sync） | 第二处 chromium，与上处无法共享实例 |
| `app/skills/produce/tts2.py`（piper） | onnx 模型 + ffmpeg（运行时在 `D:/om-runtime`） | 推理占用主进程内存/线程池 |
| `app/skills/produce/video_compose.py` | ffmpeg 密集计算 | 分钟级长任务阻塞 + 崩溃风险 |
| `capabilities/scrapling/spiders/` | scrapling 引擎 + SessionManager（cookie/反爬状态） | 爬虫被封/卡死拖累主 API |
| `app/adapters/*`（deepseek / qwen_vl / image_gen / video_gen / media_provider） | 纯 httpx 出站 | 轻依赖，无进程内痛点 |

### 1.3 已验证的外置范式（grid_detect 四步）

```
核心下沉（独立模块，进程内外共用）
  → capability_service 注册（/tools /tools/{name}/call /health）
  → 配置切换（Settings.grid_service_url：空=进程内，非空=HTTP）
  → 双跑契约测试（同断言跑 InProcess 与 Http，外置前后行为一致）
```

## 2. 评估矩阵（15 功能域结论）

### 外置档（按性价比排序）

| 域 | 目标服务 | 判定 | 理由 |
|---|---|---|---|
| `app/cards/export.py`（HTML→PNG） | **browser-service** | 第一档 | chromium 出主进程，内存立减；最痛 |
| `app/services/qr_worker.py`（登录扫码） | **browser-service** | 第一档 | 与上处合并，共享浏览器实例池 |
| `capabilities.video.skills.tts2`（piper TTS） | **media-service** | 第一档 | onnx+ffmpeg 计算域，路径进→路径出 |
| `app/skills/produce/video_compose.py`（拼接/转码/字幕） | **media-service** | 第一档 | ffmpeg 密集，分钟级长任务 |
| `capabilities.scrapling`（xhs/抖音/B站爬虫） | **spider-service** | 二档（可选） | 自带 session 状态+反爬对抗；当前低频不急 |

### 留进程内（外置=断链或零收益）

| 域 | 理由 |
|---|---|
| content_search（Tavily/Serper/Reddit/HN/GitHub/YouTube/热榜 11 源） | 纯 httpx 出站，已 source 插件化，外置纯增 RPC 开销 |
| messaging（飞书/微信收发） | 纯 webhook，轻量低频 |
| image_gen / video_gen API 适配（万相/火山/可灵） | 本就是 HTTP 出站；二档看稳定性再定（收益是进程隔离而非解耦） |
| copywrite / analyze / VL / model_router | 轻调用 + LLM 熔断器（llm_circuit）是全局状态需一致性 |
| pool_monitor（选题池 + APScheduler） | DB 强耦合 + 定时调度 |
| 确认闸门 / 澄清 / 分镜 LLM 编排 / guardian / file_ops(core) | 会话语义与循环控制，外置=断链 |

## 3. 目标架构

```
主 API 进程（瘦身目标：只剩循环/协议/DB/SSE/轻量纯函数）
  ReAct 循环 · 治理上下文 · 权限门禁 · CompositeTransport
        │ 按 capability.toml 的 runtime 声明自动路由
        ├── inprocess（默认，永久保留，一键回退）
        ├── browser-service  :8101  render_html / qr_scan
        ├── media-service    :8102  tts_piper / video_compose（+进度通道）
        └── spider-service   :8103  spider_sync / xhs_search（二档）

capability.toml 声明式编排（关键新增）：
  [cards]
  runtime = "browser"      # inprocess | browser | media | spider
  [video]
  runtime = "media"
  ...空缺默认 inprocess
```

**声明即拓扑**：拆/不拆、换端口、一键回退，全部只改 toml，代码零动。

## 4. 分阶段执行

> 原则沿用四期：每阶段结束主干可跑；全部走 grid_detect 四步；真机/云服务验证由大哥手动触发。

### 五期-A：browser-service（先啃最痛的）

| 步骤 | 改动点 | 验收 |
|---|---|---|
| A1 核心下沉 | `app/cards/export.py` 渲染逻辑抽 `render_html(html, out_path, viewport) -> dict` 纯函数；qr_worker 的扫码截屏同理抽 `capture_qr(...) -> dict` | 纯函数模块进程内外共用，主调用方行为不变 |
| A2 服务注册 | `browser_service/main.py`：工具 `render_html` / `capture_qr`，协议三方法；playwright 实例池（lazy 启动、崩溃自动重启） | `uvicorn browser_service.main:app --port 8101` 独立启停，health 可探 |
| A3 配置切换 | `Settings.browser_service_url`（空=进程内）；两个调用点走能力访问层（同 grid_capability 手法） | url 置空=原行为，置地址=走服务；不重启回退 |
| A4 双跑契约 | 同断言（同一 HTML 产出同尺寸 PNG；扫码截图非空）跑进程内与 HTTP | 主进程源码不再 import playwright |

**验收**：主 API 进程内 `grep playwright` 零命中；卡片出图/扫码功能双模式全绿。

### 五期-B：capability.toml runtime 字段（声明即拓扑）

| 步骤 | 改动点 | 验收 |
|---|---|---|
| B1 toml 扩展 | 各域加 `runtime` 字段（默认 inprocess） | toml 解析兼容旧文件（无字段不报错） |
| B2 装配接线 | 启动时读 toml → 按 runtime 建 HttpTransport → 注册进 CompositeTransport | 改 toml 重启即切换；不存在的服务地址 → 启动告警 + 该域回退 inprocess |
| B3 契约 | 装配结果快照测试（每域路由到哪，随 toml 锁定） | 改声明必可见 |

**验收**：grid_detect 的 `grid_service_url` 一类散配置统一收编进 toml 声明。

### 五期-C：长任务进度通道（前置补课，media 依赖它）

| 步骤 | 改动点 | 验收 |
|---|---|---|
| C1 服务侧 | capability_service 增 `POST /internal/events`（服务把 progress 事件回推主进程） | 事件带 turn_id/进度值，schema 沿用契约带① |
| C2 主进程侧 | 收到 /internal/events 转发进 sse_bus（现有流，前端零改动） | 前端进度条在服务模式下照常走动 |
| C3 契约 | 事件透传双跑（进程内直发 vs 服务回推，前端收到同一序列） | 改进度协议必红 |

**验收**：TTS/合成在服务模式下前端进度与进程内模式一致。

### 五期-D：media-service

| 步骤 | 改动点 | 验收 |
|---|---|---|
| D1 核心下沉 | tts2（piper 推理）与 video_compose（ffmpeg 拼接/转码/字幕）抽纯函数模块 | 与 A1 同 |
| D2 服务注册 | `media_service/main.py`：`tts_piper` / `video_compose`；长任务走 C 的进度通道 | :8102 独立启停 |
| D3 配置切换 | toml `[video] runtime = "media"` | 视频链路双模式全绿 |
| D4 双跑契约 | 同一输入音频/成片字节级或元数据级一致（时长/分辨率） | 回退零成本 |

**验收**：主 API 进程内不再加载 onnx / 调 ffmpeg。

### 五期-E：spider-service（可选，看运营节奏）

scrapling 引擎 + SessionManager 整体迁出。前置依赖 C（爬取进度）与浏览器服务经验。当前低频，顺延不做阻塞项。

## 5. 不外置清单（红线重申）

1. **确认闸门 / 澄清三分层 / 分镜编排**——会话与循环控制，外置=断链；
2. **llm_circuit 熔断器**——全局一致状态，进程外无法可靠共享；
3. **pool_monitor / asset_library / task_plan**——DB 强耦合；
4. **content_search 11 源 / messaging**——轻 HTTP，外置纯增开销；
5. **内核 primitive 表**——协议工具，永远进程内。

---

## 6. 风险与坑（前置声明）

1. **playwright sync vs async**：qr_worker 用 sync API、cards 用 async——服务端统一 async（服务进程无既有事件循环包袱），sync 调用点在 A1 一并改造；
2. **文件路径共享**：服务与主 API 同机（共享文件系统），路径传递沿用 grid 模式；跨机部署时工具内改 base64，协议不变；
3. **chromium 部署**：browser-service 需独立 `playwright install chromium`，部署文档与启动脚本随 A2 交付；
4. **长任务超时**：media 任务分钟级，HttpTransport 超时按工具配置（tts 60s / compose 600s），进度靠事件通道而非长连接等待；
5. **回退成本**：所有服务配置留空即回进程内，InProcess 永久保留（四期已验证）；
6. **真机成本**：验证一律离线 mock/单测/契约双跑；真机调用（TTS/生图/生视频）由大哥手动触发；
7. **前端零改动**：SSE 事件名与结构不变（含遗留 `multi_image_video_progress` wire 契约），服务化对前端透明。
