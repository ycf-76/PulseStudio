# Development SOP — 文档驱动·参考验证·测试门控·文档验收

> 本SOP是你唯一的开发流程权威。任何AI辅助开发必须严格遵循，不得绕过任何步骤。
> 核心原则：**文档是唯一真理，测试是唯一通行证，验收是唯一终点。**

---

## 零、总流程概览

```
┌─────────────────────────────────────────────────────────────────────┐
│                    开发SOP 全流程（6阶段）                           │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  Phase 0: 需求锚定 ──→ Phase 1: 方案设计 ──→ Phase 2: 实现编码      │
│      │                    │                    │                     │
│      ▼                    ▼                    ▼                     │
│  [文档对齐]           [参考验证]           [质量门控]                │

│      │                    │                    │                     │

```

**铁律：每个Phase必须完成后才能进入下一个Phase。任何Phase不通过，回退到上一个Phase。**

## Phase 0: 需求锚定 — 文档是唯一真理

### 0.1 定位需求文档

**必须**找到描述该功能的设计文档/需求文档。来源优先级：

| 优先级 | 来源 | 说明 |
|--------|------|------|
| P0 | `docs/` 目录下的设计文档 | 项目正式文档 |
| P1 | GitHub Issue / Feature Request | 有明确描述的issue |
| P2 | 用户口头描述 | 需要补写文档后才能开始 |

**如果没有文档，先写文档，再开始开发。禁止无文档开发。**

### 0.2 提取需求要素

从文档中提取并记录以下要素（写入工作日志）：

```
需求ID: [从文档/issue中获取]
需求标题: [一句话描述]
需求来源: [文档路径/issue链接]
功能描述: [文档原文摘录，不脑补]
验收标准: [文档中描述的期望效果，逐条列出]
涉及模块: [后端/前端/全栈]
依赖关系: [依赖哪些已有模块/外部服务]
```

### 0.3 核心路径影响评估

对照项目核心路径评估影响：

```
核心路径: search → analyze → copywrite → image_plan → image_gen → image_review → final_review → publish

本次改动是否影响核心路径？ [是/否]
如果影响，影响哪个环节？ [具体环节]
如果影响，需要哪些额外回归测试？ [列出]
```

### 0.4 五道关卡预检

| 关卡 | 检查内容 | 通过条件 |
|------|----------|----------|
| K1 | 是否属于核心路径？ | 是→P0；用户明确要求→P1；觉得可能有用→**停下来不写** |
| K2 | 现有代码有无类似功能？ | 有未完成→先完成；有已完成→复用扩展；无→继续 |
| K3 | 能否100行内写MVP？ | 能→写；不能→先写最小X验证 |
| K4 | 会让已有功能变难改吗？ | 逐项检查依赖/步骤数/组件数 |
| K5 | 30分内能写完测试吗？ | 能→TDD；不能→功能太复杂需拆小 |

**任何一道关卡不通过，停下来解决问题，不进入Phase 1。**

## Phase 1: 方案设计 — 参考验证，不脑补

### 1.1 方案设计原则

**核心要求：拿不准的点必须根据文档记录对应的开源项目来参考，不能自己擅自脑补！**

具体执行：

| 场景 | 正确做法 | 错误做法 |
|------|----------|----------|
| 文档有明确方案 | 严格按文档实现 | 觉得"更好的方式"擅自改 |
| 文档方案模糊 | 查找文档中引用的开源项目参考 | 自己脑补一个方案 |
| 文档未提及某细节 | 记录为"待确认点"，查开源参考后补入文档 | 假设一个默认行为 |
| 多种实现方式可选 | 文档有说明按文档；无说明则查开源参考后记录ADR | 凭直觉选一个 |

### 1.2 开源参考验证流程

当遇到拿不准的实现细节时：

```
1. 明确不确定点：[具体是什么不确定]
2. 查找文档中的参考来源：
   - 文档是否引用了开源项目？ → 查阅该项目源码/文档
   - 文档是否给出了参考链接？ → 阅读参考链接
3. 如果文档无参考：
   - 搜索同类开源项目的实现方式（至少查2个）
   - 记录参考项目和具体文件/代码位置
4. 形成决策，记录ADR（Architecture Decision Record）
5. 将决策补入项目文档（docs/对应文档）
```

**参考记录格式（必须写入工作日志）**：

```
不确定点: [描述]
参考项目1: [项目名/URL] → [具体文件/代码位置] → [该项目的做法]
参考项目2: [项目名/URL] → [具体文件/代码位置] → [该项目的做法]
最终决策: [选择了什么方式]
决策理由: [为什么选这个，基于什么参考]
ADR编号: [ADR-XXX]
```

### 1.3 方案输出物

Phase 1 完成时必须产出：

```
1. 实现方案说明（含模块划分、接口设计、数据流）
2. 文件放置规划（每个文件放到哪个目录，为什么放这里）
3. 不确定点清单（每个点都有开源参考支撑）
4. ADR记录（如有架构决策）
5. 测试计划（测什么、怎么测、预期结果）
```

### 1.4 文件放置规范（功能必须放到指定位置）

| 类型 | 放置位置 | 上限 | 说明 |
|------|----------|------|------|
| Skill定义 | `backend/app/agents/prompts/skills/` | 150行.md | 按category分目录 |
| Skill执行 | `backend/app/tools/` | 150行.py | 公共逻辑抽到tools/common/ |
| Skill注册 | `backend/app/tools/registry.py` | 一行 | 必须注册 |
| Router | `backend/app/api/routers/` | 150行.py | 业务逻辑在Service层 |
| Schema | `backend/app/api/schemas/` | - | 请求/响应模型 |
| Service | `backend/app/services/` | 300行.py | 按职责拆分 |
| 节点函数 | `backend/app/agents/nodes/` | 200行.py | 子函数抽到_helper.py |
| 前端组件 | `frontend/src/components/` | 500行.vue | 独立文件，禁止内联 |
| 前端Store | `frontend/src/stores/` | - | ≤2个Store依赖 |
| 测试 | `backend/tests/` | - | 与源码结构对应 |
| 契约测试 | `backend/tests/contract/` | - | 接口契约验证 |

**禁止随意堆砌：每个新文件必须说明为什么放在这个位置、与同目录文件的关系。**

## Phase 2: 实现编码 — 质量门控

### 2.1 编码前检查清单

```
□ Phase 0 需求锚定完成（有文档、有验收标准）
□ Phase 1 方案设计完成（有方案、有参考、有测试计划）
□ 文件放置位置已确定（符合1.4规范）
□ 现有代码已阅读（理解上下文、调用方、依赖方）
□ 接口设计已确认（不与现有接口冲突）
```

### 2.2 编码质量标准

**实现的功能必须满足：专业性、可维护性、易拓展性、高可用性**

| 维度 | 标准 | 检查方法 |
|------|------|----------|
| 专业性 | 遵循项目现有代码风格和模式 | 对比同目录已有代码 |
| 可维护性 | 单文件不超上限；函数单一职责；无裸try/except | 行数统计+代码审查 |
| 易拓展性 | 用组合替代继承；接口抽象；配置驱动 | 新增功能不需改核心代码 |
| 高可用性 | 关键路径有降级；错误有记录；启动有健康检查 | startup_health+降级逻辑 |

### 2.3 编码过程规范

```
1. 先写接口/类型定义（Schema/Protocol/ABC）
2. 再写核心逻辑（最小可用版本）
3. 然后写注册/接入代码（registry/router/include）
4. 最后写配置/常量（不硬编码）
```

**每完成一个子步骤，立即自检**：

```
□ 文件行数是否超限？
□ 是否引入了不必要的依赖？
□ 是否遵循了现有代码模式？
□ 错误处理是否完整（无裸吞异常）？
□ 日志记录是否充分？
```

### 2.4 禁止事项

| 禁止 | 原因 |
|------|------|
| ❌ 脑补实现细节 | 必须有文档或开源参考支撑 |
| ❌ 随意放置文件 | 必须按1.4规范放到指定位置 |
| ❌ 写了不注册 | 死代码是负债 |
| ❌ 一个函数做两件事 | 违反单一职责 |
| ❌ 裸try/except吞错 | 必须startup_health记录+logger |
| ❌ 内联子组件 | 必须独立文件 |
| ❌ 硬编码配置 | 必须走配置/环境变量 |
| ❌ 循环依赖 | Store/模块间禁止循环引用 |

## Phase 3: 测试验证 — 真实通过，不假通过

### 3.1 测试铁律

**按顺序每做完一个任务，一定要写测试案例，测试通过才能继续下一个任务，不能假测试通过直接执行下一个任务！**

```
实现一个功能 → 写测试 → 运行测试 → 测试真实通过 → 继续下一个功能
                 ↑                         |
                 |______测试失败 → 修复 → 重新运行 ____|
```

### 3.2 测试分层

| 层级 | 范围 | 位置 | 必须性 |
|------|------|------|--------|
| L1 单元测试 | 单个函数/类 | `tests/test_*.py` | **必须** |
| L2 集成测试 | 模块间交互 | `tests/test_*_integration.py` | 涉及多模块时必须 |
| L3 契约测试 | 接口契约 | `tests/contract/test_*_contract.py` | 涉及API/协议时必须 |
| L4 E2E测试 | 核心路径 | `tests/test_*_e2e.py` | 影响核心路径时必须 |

### 3.3 测试编写规范

每个测试必须包含：

```python
def test_<功能>_<场景>_<预期结果>():
    """
    测试: [功能名称]
    场景: [具体场景描述]
    预期: [预期结果，与文档验收标准对应]
    文档依据: [文档路径#章节]
    """
    # Arrange: 准备测试数据
    ...

    # Act: 执行被测操作
    ...

    # Assert: 验证结果
    ...
```

### 3.4 测试执行与验证

**必须真实运行测试，检查输出，确认通过。禁止以下行为**：

| 禁止行为 | 说明 |
|----------|------|
| ❌ 只写测试不运行 | 测试可能本身有bug |
| ❌ 看到测试报错直接跳过 | 必须修复到通过 |
| ❌ 用skip/xfail掩盖失败 | 除非是已知缺陷并记录了issue |
| ❌ 修改测试来适配错误实现 | 应修改实现来通过测试 |
| ❌ 假设测试通过 | 必须看到pytest输出ALL PASSED |

**测试通过标准**：

```
1. pytest 退出码为 0
2. 所有测试用例状态为 PASSED（无FAILED、无ERROR）
3. 无跳过的测试（除非有明确标注原因）
4. 覆盖了验收标准中的每一条
```

### 3.5 测试执行命令

```bash
# 后端测试
cd backend
python -m pytest tests/test_<模块>.py -v --tb=short

# 全量测试（集成前）
python -m pytest tests/ -v --tb=short

# 契约测试
python -m pytest tests/contract/ -v

# 代码质量检查
ruff check app/
mypy app/
```

## Phase 4: 集成回归 — 核心路径不回退

### 4.1 集成检查清单

```
□ 新功能已注册到对应registry/router
□ 新功能已接入调用链
□ 运行全量测试通过
□ 核心路径回归测试通过
□ 无新增TODO超过5个
□ 无新增超过500行的文件
□ 无新增裸try/except
□ 无新增循环依赖
```

### 4.2 核心路径回归

**任何改动后，必须验证核心路径能跑通**：

```
核心路径: search → analyze → copywrite → image_plan → image_gen → image_review → final_review → publish

验证方式:
1. 运行核心路径相关测试
2. 如有前端改动，验证UI渲染正常
3. 检查SSE事件流正常
```

### 4.3 副作用检查

```
改了A，检查B：
- 改了后端Service → 检查对应Router/Schema
- 改了Skill → 检查registry注册/节点调用
- 改了前端Store → 检查所有使用该Store的组件
- 改了API接口 → 检查前端API调用
- 改了数据库模型 → 检查迁移脚本
```

## Phase 5: 验收关闭 — 文档匹配

### 5.1 验收铁律

**验收需要达到文档所描述的效果。不是"代码写完了"就算完成，是"效果与文档描述一致"才算完成。**

### 5.2 验收检查表

逐条对照Phase 0提取的验收标准：

```
验收标准1: [文档描述] → 实际效果: [验证结果] → [通过/不通过]
验收标准2: [文档描述] → 实际效果: [验证结果] → [通过/不通过]
...
验收标准N: [文档描述] → 实际效果: [验证结果] → [通过/不通过]
```

**任何一条验收标准不通过，回退到Phase 2修复。**

### 5.3 验收方式

| 验收类型 | 方式 | 说明 |
|----------|------|------|
| 功能验收 | 运行测试+手动验证 | 测试覆盖+实际操作确认 |
| 接口验收 | API调用验证 | curl/Postman调用确认返回格式 |
| UI验收 | 页面渲染验证 | 截图对比/实际操作 |
| 性能验收 | 基准测试 | 关键路径耗时不退化 |
| 文档验收 | 文档更新确认 | 文档与实现一致 |

### 5.4 关闭条件

所有以下条件满足才能关闭任务：

```
□ 所有验收标准通过
□ 所有测试真实通过（非假通过）
□ 核心路径回归通过
□ 代码质量检查通过（ruff/mypy）
□ 无遗留TODO超过5个
□ ADR已记录（如有架构决策）
□ 工作日志已更新
□ git commit（message: "feat: <功能描述>"）
```

## 快速参考：常见场景SOP

| 场景 | 执行路径 |
|------|----------|
| 新增Skill | P0(读docs)→P1(查同类skill参考)→P2(写md+py+注册)→P3(单元测试)→P4(核心路径)→P5(功能验收) |
| 新增Router | P0(读docs)→P1(查同类router参考)→P2(写router+schema+service)→P3(契约测试)→P4(全量测试)→P5(接口验收) |
| 新增前端组件 | P0(读docs)→P1(查同类组件参考)→P2(写vue+store)→P3(渲染测试)→P4(UI回归)→P5(UI验收) |
| 修复Bug | P0(读bug描述)→P1(定位根因+查参考)→P2(最小修复)→P3(回归测试)→P4(核心路径)→P5(验证修复) |
| 重构代码 | P0(明确重构目标)→P1(小步拆分方案)→P2(每步可验证)→P3(每步测试)→P4(每步回归)→P5(效果对比) |

## 与项目架构文档的关系

本SOP是项目架构文档的**执行层补充**：
- 架构文档定义了"什么是对的"（分层边界/契约/禁止项）：
  - `docs/内核-能力分层架构方案.md` — 内核与能力的职责划分
  - `docs/skills-architecture.md` — Skills 后处理管道的定位
  - `docs/能力外置服务化执行计划.md` — 能力外置的分期落地
- 本SOP定义了"怎么做到对的"（流程/步骤/检查点）
- 两者不冲突，本SOP在架构文档的基础上增加了流程强制性和测试门控
